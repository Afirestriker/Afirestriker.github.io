CASE STUDY / PLATFORM CAPABILITY

One form engine.
Many possibilities.

Replacing repeated form implementations with a configuration-driven engine — and giving engineers a better way to author the schemas behind it.

MY ROLE
Schema design, engine development, prototypes, documentation and visualizer
COLLABORATION
Developed with feedback from the UI team and integrated across platform screens
CORE TECHNOLOGIES

01 / THE PROBLEM

A new connector shouldn’t
mean another bespoke form.

Each connector, workflow node and tenant screen needed its own fields and validation. Handwritten forms repeated implementation work and made new configurations another frontend development task.

The UI team explored existing approaches and agreed to build a form capability suited to the platform. I took on the design and implementation, then developed it through prototypes and team feedback.

The design question: How can one engine support different field types, dependencies and validation rules while keeping the resulting interfaces consistent?

02 / THE APPROACH

Configuration first.
Usability throughout.

Prove the behavior before scaling it

I built two proofs of concept. Feedback from the team surfaced questions about validation, rendering performance, loading states and component remounting. I used the second prototype to address those concerns and walk through the intended implementation.

Build an engine that can evolve

The engine renders forms from backend JSON configuration. Its capabilities grew to include conditional visibility, runtime option loading, cascading selects and specialized field types. I maintained the schema specification and added capabilities with backward compatibility in mind.

Make authoring part of the solution

Once the renderer was in use, writing the form configuration became an important part of the work. I built a schema visualizer with live preview, validation and in-app documentation so engineers could inspect what they were building while authoring it.

04 / ENGINEERING DECISIONS
Make the common path reusable.
Keep room for exceptions.
ConcernApproach in the platform work
Repeated field implementationsUse a shared renderer and schema definitions across different screens.
Dependent fields and optionsSupport conditional visibility, dynamic options and cascading selections.
Node-specific configurationFetch and cache form configuration by node type, in collaboration with the UI team.
Existing configurationsVersion and document schema changes, preserving compatibility as features grow.
Developer experienceProvide a visualizer, live preview and documentation alongside schema authoring.

05 / THE OUTCOME
A reusable capability.
Beyond a single screen.
The form builder is used across connector, workflow, scheduler, tenant and other platform screens. New forms can be introduced through configuration rather than another separate form implementation.
My ownership covered the engine, schema design, documentation, visualizer and subsequent extensions. The wider UI team contributed feedback and helped bring the capability into the platform.
What this work demonstrates: turning a recurring implementation problem into a reusable platform capability, then supporting its adoption through developer tooling and documentation.
